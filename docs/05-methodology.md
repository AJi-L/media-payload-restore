# 05 · 方法论：怎么定位这类改写 / 怎么取明文

这篇讲两件事：**（A）取明文的一种做法**，**（B）定位"负载被改写"的套路**。

---

## A. 取明文：把播放器当解密黑盒

### A.1 总体

受保护文件的密钥在发行方的播放器里，我们不去逆它，而是让播放器自己解密，
然后把解密后的流截下来。做法是**替换播放器依赖的 FFmpeg 解复用模块**
（`avformat-58.dll`）为一个"代理 DLL"：

```
                       ┌─────────────── 代理 DLL ───────────────┐
播放器 ── 调用 ──────► │ 转发全部导出符号（尾跳）              │
                       │ avformat_open_input 返回后：           │
                       │   取 (*ps)->pb   —— FFmpeg 内部的      │
                       │   AVIOContext，正是解复用器读的地方     │
                       │   avio_seek(0) + avio_read 循环写盘     │
                       └────────────────────────────────────────┘
```

关键点：**解密逻辑在播放器自己注册的私有协议读回调里**，
所以常规的 `avio_alloc_context` 钩子根本不会被调用
（`avformat_open_input(url=stream:...)` 里的 `stream:` 就是它自己注册的协议）。
但 `avformat_open_input` 是**我们**实现的，返回后可以直接从
`AVFormatContext.pb` 拿到 FFmpeg 为这个协议建好的 `AVIOContext`。

- 32 位 FFmpeg 4.x：`AVFormatContext.pb` 在偏移 16
- `avio_size()` 与源文件等长 → 说明是**逐字节原地解密**

### A.2 两个必要的准备

**（1）让播放器以普通权限运行。**
这类播放器常声明 `requireAdministrator`，此时它跑在高完整性级别，
普通权限进程读不到它的内存。把 PE 内嵌清单里的 `requireAdministrator`
**等长替换**成 `asInvoker`（尾部补空白保持长度），改**自己的副本**再运行即可：

```powershell
python src\dll-proxy\patch_manifest.py "D:\player\YourPlayer.exe"
```

**（2）编译代理 DLL。**
`gen_proxy.py` 读导出表生成转发存根，`proxy.c` 是本体：

```powershell
cd src\dll-proxy
python gen_proxy.py
gcc -m32 -O2 -shared -o ..\..\build\avformat-58.dll proxy.c ..\..\build\gen.c ..\..\build\gen.S ..\..\build\gen.def
```

> 必须是 **32 位** 编译（目标播放器是 32 位），并且导出表要与之**逐一对齐**。
> 换别的播放器时，把它的 `avformat-*.dll` 导出表导出成 `avformat_exports.json` 即可复用。

### A.3 自动"点播放"

播放器启动后需要点一下"播放"才开始解密。脚本按**窗口尺寸**找对话框
（`EnumWindows` + `GetWindowRect`），再按相对坐标发鼠标事件。
换皮肤/分辨率时把 `Click-Play` 里的尺寸与坐标改掉即可。

## B. 定位"负载被改写"的套路

### B.1 先固定事实，再猜机制

不要一上来就猜算法。先把**能确认的事实**统计出来，例如：

- 每个 slice 前是不是都多了同一个字节？（对全部切片做统计，而不是抽查）
- 头部字段在"去掉那个字节"之后能不能解析？
- 解析出来的哪些字段是合理的、从哪个字段开始不合理？

"从哪个字段开始不合理"这个信息价值极高 —— 它直接告诉你改写发生在哪里。

### B.2 用"有确定预期的字段"当探针

这是本项目最关键的一招。字段里有一批**值是可以预期的**，最典型的是：

- **IDR 的 `frame_num` 必须是 0**
- 紧随 IDR 之后的第一个参考帧应当是 1
- `pic_order_cnt_lsb` 应当单调、步长固定

于是可以**穷举比特偏移**：

```
for k in 0..N:
    跳过前缀 + k 个比特，解析 frame_num / poc
    看哪个 k 让这些"应该对得上"的值全部合理
```

本项目里 `k = 1` 一举命中，并立刻解释了一连串旧谜团。

### B.3 警惕"看起来有效的补丁"

如果某个改动让**一部分**问题消失（比如"错误率从 100% 降到 12%"），
要特别小心 —— 那可能不是"修好了"，而是把**系统性问题降级成了概率性表现**。

本项目就吃过这个亏：曾经以为"PPS 的 `weighted_pred_flag` 要改成 0"、
"QP 要偏移 -2"、"B 帧要额外丢 1 bit"，这些补丁都能让一部分切片解对，
但它们全是**在补偿那 1 个比特**，把排查方向带偏了很久。

**判别方法**：问自己"这个改动**为什么**会让它变好？机制是什么？"
如果答不上来、只有经验相关性，那就先别信。

### B.4 用"1/8"这类比例做交叉验证

概率性的现象往往对应某个边界条件。本项目里 `Reference 4 >= 4` 的出现率是
**12.14% ≈ 1/8**，而"头部正好字节对齐"的条件恰好是 1/8 概率 ——
这条比例关系成了确认真因的决定性证据。

遇到类似"某个小数"时，不妨想想它是不是 `1/2^k`、是不是某个模运算的边界。

### B.5 最后：用标准解码器做全片验收

还原是否真的正确，用标准工具说话：

```powershell
ffmpeg -hide_banner -v error -i out.mp4 -f null -
```

**输出为空**才算通过。注意把"末帧 DTS"那类已知无害提示过滤掉，
否则会误判（见 `docs/03-container-and-remux.md`）。
